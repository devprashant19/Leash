# Architecture Survey — Phase 4 (improve-codebase-architecture)
Date: 2026-11-21

## 1. Current State
- `ingots/policy`:
  - Pure rule evaluation (`decide` has no `uses` clause).
  - State serialization (`encode_state` / `decode_state_bytes`).
  - Canonical policy hashing (`keccak256("LEASH_POLICY_V1" || enc(policy))`).
  - Fully decoupled from I/O, storage, and EVM specifics.
- `ingots/module`:
  - `LeashModule` forwards calls via `Safe.execTransactionFromModule`.
  - Reentrancy mutex via transient flag.
  - Reverts with typed custom error selectors in `Execute`.
  - Returns `(bool ok, u8 code)` in `TryExecute`.
  - Bytecode: 23,050 bytes (< 24,576 bytes limit; headroom 1,526 bytes).
- `ingots/cli`:
  - Pure CLI bridge to `policy::decide`, `explain`, `fingerprint`, and `replay`.
  - Strict effect least privilege: `check` has 0 filesystem effects; only `replay` has `Fs`.
  - Golden tests: 14 fixtures passing.

## 2. Findings & Fragility Areas to Address
1. **Contract Bytecode Headroom**:
   - Current bytecode is 23,050 bytes (headroom 1,526 bytes).
   - Adding complex features to `LeashModule` (e.g. per-agent policy storage and decoding) must be kept lean to prevent exceeding 24,576 bytes.
   - Recommended strategy: Keep policies stored in a compact encoded representation or structured storage, reuse helper functions, and avoid duplicate code paths.
2. **Compile-time vs Runtime Validation (`validate.fe`)**:
   - `validate(policy: Policy) -> PolicyCheck` should be a pure function in `ingots/policy/src/validate.fe`.
   - Used by:
     - Compile-time assertion `static_assert` or compile-fail tests.
     - Runtime in `LeashModule.SetAgent` / `SetPolicy`.
     - Native CLI `leash validate`.
3. **AgentState Expansion**:
   - `AgentState` needs tracking for:
     - `action_window: Window24` for rate limiting (A9).
     - `cooldown` tracking: `last_action: Timestamp` (A10) (already present in `AgentState`).
     - Circuit breaker: `denial_window: Window24`, `tripped: bool` (B3) (`tripped` already present).
     - Token windows: `token_windows: [Window24; MAX_TOKENS]` (A6).
4. **Order of Evaluation in `decide`**:
   - Must strictly follow context §6:
     1. Paused
     2. CircuitTripped
     3. SessionExpired
     4. OutsideTradingHours
     5. CooldownActive
     6. DelegateCallBlocked
     7. TargetNotAllowed
     8. Calldata shape (MalformedCalldata / SelectorNotAllowed)
     9. RateLimited
     10. PerTxCapExceeded
     11. WindowCapExceeded
     12. Protocol guard for target kind (ERC-20: RecipientNotAllowed -> UnlimitedApproval -> TokenCapExceeded)

## 3. Plan of Execution
We will implement the Phase 4 features in strict priority order:
1. Compile-time policy validation (`validate.fe` + `PolicyCheck` + `test/compile_fail/`)
2. Recipient allowlist (A8) + rate limit (A9)
3. Per-agent policies (B2) + ADR-007
4. Machine-readable CLI output (`--json`) + agent-friendly deny explanations (D1, Tier A)
5. Cooldown between transactions (A10)
6. Per-token rolling windows (A6)
7. Auto-pause circuit breaker (B3)
8. Trading hours (A11)
9. Asymmetric limit changes (B4) + ADR-008
10. TOML policy files (D4) + ADR-009
